## Orchard Core 3.0.2

**Release Date:** Not yet released

This is a service release for Orchard Core 3.0. It contains security hardening for Liquid authoring and rendered HTML. Review the behavior changes below before upgrading.

## Security

### New `ManageLiquidTemplates` permission

Authoring executable Liquid now requires the new security-critical `ManageLiquidTemplates` permission, in addition to any feature-specific permission. It is granted to the Administrator and Editor roles by default, and existing Editor roles are updated automatically when the tenant is upgraded.

The permission is required to:

- Edit templates and admin templates, and use template preview (together with `ManageTemplates` or `ManageAdminTemplates`).
- Create or edit content items containing a `LiquidPart` or a Meta social plugin `FacebookPluginPart`, including when such content items are nested in other content items (e.g. in a `FlowPart` or `BagPart`).
- Enable `Render Liquid` on HTML or Markdown parts and fields, and create or edit content items whose type has `Render Liquid` enabled.

These rules are enforced for the admin editors, the content REST API, and MetaWeblog.

!!! warning
    Users in custom roles, or in the Author and Contributor roles, can no longer create or edit content of the types listed above unless their role is granted `ManageLiquidTemplates`. Only grant this permission to users trusted to author server-side templates.

### HTML is sanitized when rendered instead of when saved

The exact HTML or Markdown authored by users is now persisted unchanged, and `Sanitize Html` is applied to the final rendered output, after Liquid and shortcodes are processed. This also protects content that was stored before upgrading.

This applies to the HTML Body Part, HTML Field, Markdown Body Part, Markdown Field, and HTML Menu Item Part, for the Detail and Summary displays, preview, `BodyAspect`, and GraphQL rendered HTML.

!!! warning
    For the HTML Body Part and HTML Field, markup that is produced by Liquid or shortcodes is now sanitized too when `Sanitize Html` is enabled, which is the default (Markdown output was already sanitized this way). For instance, `<iframe>`, `<form>`, `<script>`, or `<style>` elements generated by a Liquid template or a shortcode are now removed from the output. To keep such markup, either disable `Sanitize Html` on the part or field for trusted authors, or allow the required elements by [configuring the HTML sanitizer](../reference/modules/Sanitizer/README.md#configuring-the-sanitizer).

### Menu item URLs

HTML menu item and link menu item URLs whose scheme is not allowed by the HTML sanitizer, such as `javascript:`, are no longer rendered. This also covers menu items that were imported or created through APIs, which bypass the menu item editor's URL validation. The persisted menu items are not modified.

## Title Module

When the title of a content type is generated from a pattern, the `TitlePart` handler now also evaluates the pattern when a content item version is published. Publishing a version that wasn't created or updated in the same request, such as republishing an unpublished content item, now sets its display text from the pattern. The pattern is still evaluated only once per content item in a request, so a title already generated when the item was created or updated isn't evaluated again on publish.

## Media Module

### ImageSharp 4

The media image processing is upgraded to ImageSharp 4.1 and ImageSharp.Web 4.0, which fix the vulnerabilities reported for ImageSharp 3.1.12 and lower. The query string arguments, media profiles, tokens, and the `resize_url` and `img_tag` Liquid filters work as before.

The ImageSharp services and middleware, the token service, and the Azure Blob Storage and Amazon S3 image caches are now provided by the `OrchardCore.Media.ImageSharp` package, which the `OrchardCore.Media` package depends on. The `OrchardCore.Media`, `OrchardCore.Media.Azure` and `OrchardCore.Media.AmazonS3` packages no longer reference the Six Labors packages directly. The types moved from the `OrchardCore.Media` assembly keep their namespaces and are forwarded to the new assembly, so code compiled against previous versions keeps working.

ImageSharp checks for a Six Labors license when building a project that references it directly. The `OrchardCore.Media.ImageSharp` project includes an assembly-scoped community license, so building Orchard Core from source doesn't require a license. Applications referencing the Orchard Core packages get ImageSharp through the `OrchardCore.Media.ImageSharp` package and don't need a license either. Only a project of your own that references a Six Labors package directly, for instance to add an ImageSharp.Web processor, needs its own license.

If you extend ImageSharp.Web, for instance with a custom processor or image cache, update your code to ImageSharp.Web 4. Among other changes, its service registration extensions are in the `SixLabors.ImageSharp.Web` namespace instead of `SixLabors.ImageSharp.Web.DependencyInjection`, and the Azure and Amazon S3 caches are in the `SixLabors.ImageSharp.Web.Azure.Caching` and `SixLabors.ImageSharp.Web.AWS.Caching` namespaces.
