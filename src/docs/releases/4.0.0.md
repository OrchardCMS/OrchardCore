# Orchard Core 4.0.0

**Release Date:** Not yet released

**Full Changelog**: https://github.com/OrchardCMS/OrchardCore/compare/v3.0.1...v4.0.0

## Breaking Changes

### Admin Theme

Previously, `bootstrap-select` styles were included automatically in the **TheAdmin** theme. If you use `bootstrap-select` resources in your own project, you must now include the `bootstrap-select` styles explicitly. This can be done by adding the following to your Razor view:

```
<style asp-name="bootstrap-select" at="Head"></style>
```

### Admin Menu

The admin menu of **TheAdmin** theme was redesigned:

- First level items holding children are now rendered as groups: a small muted caption above the items they hold.
- A new **Navigation menu behavior** admin setting decides how the sections open and close. With `Focused`, the default, only the section of the current page is open when a page loads, as in previous versions, and opening a section also closes the others at the same level. With `Persistent`, what is expanded belongs to the user: the script restores what the user last opened, at every level, and navigating never collapses anything, so a section left open stays open from page to page. See [Navigation menu behavior](../reference/modules/Admin/README.md#navigation-menu-behavior).
- With either behavior the menu is rendered fully collapsed, and the section holding the current page is always opened, so the page being edited is always reachable in the menu.
- An item that both links to a page and holds children now renders its label as a link next to a separate `button.nav-toggle` expanding its children, instead of a single label doing both.
- Below the `md` breakpoint the menu is an off canvas drawer, toggled by a new `button.ta-sidebar-toggler` in the top bar and closed by clicking the new `div.ta-sidebar-backdrop`, pressing <kbd>Esc</kbd>, or opening a menu item. The screen is no longer reduced by the compact rail on small screens, and the rail itself now only applies from the `md` breakpoint up, where each group opens as a flyout.

This changes the markup of the menu. If you override `Navigation-admin.cshtml`, `NavigationItem-admin.cshtml`, or `NavigationItemLink-admin.cshtml`, or style the menu with your own CSS, re-check those customizations:

- The `li` of the selected item now also carries a `current` class, while `active` keeps marking it and all of its ancestors.
- The `ul` of a group carries a `nav-group-items` class, its `id` is now built from the stable hash of the item (`m{hash}`) instead of the shape's runtime hash code, and the `li` of a first level item carries a `nav-group` class. No `ul` is rendered with the `show` class anymore, and every toggle is rendered with `aria-expanded="false"`, since the expanded state is applied by the script.
- The `figcaption` of an item carries a `nav-item-row` class, the chevron is no longer wrapped in a `div.btn-nostyle`, and the label no longer carries the `d-flex` class since the style sheet lays it out.
- The filter input is now wrapped in a `div.nav-filter`.

### Admin Menu Colors

The menu of **TheAdmin** theme now uses its own surface instead of the one derived from the Bootstrap subtle backgrounds, in both the light and the dark theme. It is built on the Bootstrap gray scale of the top bar, one step darker, so that both read as one palette, and the current page is marked with the darkest gray of that same scale rather than with a color, which replaces `var(--bs-primary)` as the value of `--oc-selected-indicator-color`. The top bar itself is unchanged.

The palette is declared as CSS custom properties, so a site can rebrand the menu by redefining them, for example in a theme that depends on **TheAdmin**:

```css
:root {
    --oc-admin-accent-rgb: 73, 80, 87;
    --oc-admin-accent-strong-color: #343a40;
    --oc-admin-menu-bg-color: #f1f3f5;
    --oc-admin-menu-border-color: #dee2e6;
}
```

`--oc-admin-menu-separator-color`, `--oc-admin-menu-item-hover-bg-color`, and `--oc-admin-menu-item-active-bg-color` are now washes of `--oc-admin-accent-rgb` instead of the Bootstrap emphasis color, and `--oc-admin-menu-group-font-color`, `--oc-admin-menu-border-color`, `--oc-admin-accent-rgb`, `--oc-admin-accent-color`, and `--oc-admin-accent-strong-color` are new. `--oc-admin-accent-strong-color` is the end of the scale used where the accent has to stand out against a surface: the darkest gray in the light theme, the lightest one in the dark theme.

The compact sidebar also no longer forces a `"Segoe UI VSS (Regular)", "Segoe UI", …` font stack, so the whole admin consistently renders with the default Bootstrap sans-serif stack (`var(--bs-body-font-family)`).

The palette and the menu were checked against WCAG 2.1: every label of the menu meets AA, the current one meets AAA, and the icons, the chevrons, the selection indicator, and the scrollbar meet the 3:1 of *Non-text Contrast*. Menu labels now wrap instead of being truncated with an ellipsis, so no item becomes unreadable when the text is long, the page is zoomed, or the reader forces their own text spacing. Every control of the menu also draws a visible `:focus-visible` outline, where the sidebar previously relied on a background tint too faint to see, and the animations of the menu are turned off under `prefers-reduced-motion`.

### Display shape initialization APIs

`ShapeResult` and `DisplayDriverBase.Factory()` now use `ValueTask`-based initializer delegates. The virtual `DisplayDriverBase.Factory()` extension point also accepts typed builder and initializer state to avoid closure allocations. Derived display drivers that override the previous three-parameter `Factory()` method must migrate their override to `Factory<TBuilderState, TInitState>()`.

`DisplayDriverBase.Shape()` is now obsolete because it allocates an `IShape` immediately, even when the shape is later hidden. Use `DisplayDriverBase.Factory()` instead to defer shape creation until the shape is actually displayed.

### `IOptionsMonitor<TOptions>` for site settings-backed options

Orchard Core now has a post-commit, signal-backed `IOptionsMonitor<TOptions>` refresh pipeline for options that are populated from tenant site settings. This lets admin settings changes update the running tenant without forcing a shell release.

Custom code that previously injected `IOptions<TOptions>` and expected those values to track settings changes must switch to `IOptionsMonitor<TOptions>` and read `CurrentValue` (or `Get(name)` for named options) instead.

If your own settings UI updates values that feed those options, register Orchard Core's signal-backed `IOptionsChangeTokenSource<TOptions>` for the affected options type and request invalidation with `IOptionsUpdateNotifier` after the settings update succeeds so Orchard Core refreshes the monitor cache after the underlying YesSql session commits.

- `EmailOptions`, `EmailProviderOptions`, and `AzureEmailOptions` now participate in this refresh pipeline. `AzureEmailProviderBase` changed accordingly: it is now generic (`AzureEmailProviderBase<TOptions> where TOptions : AzureEmailOptions`), its constructor takes `IOptionsMonitor<TOptions>` instead of a `Func<AzureEmailOptions>`, and it reuses the `EmailClient` instance until the current connection string changes. Custom Azure email providers derived from the old non-generic base class must update their inheritance and constructor calls.
- `ShapeRenderingOptions` now participates in this refresh pipeline, so the **Debugging** settings screen can toggle shape debug output without forcing a shell release.
- `ReCaptchaSettings` now participates in this refresh pipeline, so enabling or updating ReCaptcha site settings takes effect without forcing a shell release. Custom code that cached `ReCaptchaSettings` from `IOptions<ReCaptchaSettings>` must switch to `IOptionsMonitor<ReCaptchaSettings>` and read `CurrentValue`.
- `RegistrationOptions` now participates in this refresh pipeline, so changes to registration settings take effect without forcing a shell release. Custom code that cached `RegistrationOptions` from `IOptions<RegistrationOptions>` must switch to `IOptionsMonitor<RegistrationOptions>` and read `CurrentValue`.
- `ExternalLoginOptions` now participates in this refresh pipeline, so changes to external login settings take effect without forcing a shell release. Custom code that cached `ExternalLoginOptions` from `IOptions<ExternalLoginOptions>` must switch to `IOptionsMonitor<ExternalLoginOptions>` and read `CurrentValue`.
- `AzureAISearchDefaultOptions` now participates in this refresh pipeline, so changes to Azure AI Search settings take effect without forcing a shell release. Custom code that cached `AzureAISearchDefaultOptions` from `IOptions<AzureAISearchDefaultOptions>` must switch to `IOptionsMonitor<AzureAISearchDefaultOptions>` and read `CurrentValue`.
- `SmtpOptions` now participates in this refresh pipeline, so changes to SMTP site settings take effect without forcing a shell release. Custom code that cached `SmtpOptions` from `IOptions<SmtpOptions>` must switch to `IOptionsMonitor<SmtpOptions>` and read `CurrentValue`.
- `SmsProviderOptions` now participates in this refresh pipeline, so changes to the enabled SMS providers and SMS provider selection take effect without forcing a shell release. Custom code that cached `SmsProviderOptions` from `IOptions<SmsProviderOptions>` must switch to `IOptionsMonitor<SmsProviderOptions>` and read `CurrentValue`.
- `AzureSmsOptions` now participates in this refresh pipeline, so changes to Azure Communication Services SMS settings take effect without forcing a shell release. Custom code that cached `AzureSmsOptions` from `IOptions<AzureSmsOptions>` must switch to `IOptionsMonitor<AzureSmsOptions>` and read `CurrentValue`.
- `TwilioOptions` now participates in this refresh pipeline, so changes to Twilio SMS settings take effect without forcing a shell release. Custom code that cached `TwilioOptions` from `IOptions<TwilioOptions>` must switch to `IOptionsMonitor<TwilioOptions>` and read `CurrentValue`.
- `SmtpEmailProviderBase` is now generic (`SmtpEmailProviderBase<TOptions> where TOptions : SmtpOptions`) and its constructor takes `IOptionsMonitor<TOptions>` instead of a `SmtpOptions` instance. Custom SMTP providers derived from the old non-generic base class must update their inheritance declaration and constructor to pass `IOptionsMonitor<TOptions>`.

### Permission Descriptions

`Permission.Description` is now a `LocalizationSource` instead of a `string`, so that permission descriptions can retain their PO context until display time. The constructors that take a `string` description are still available and create context-free sources. New constructors accept a `LocalizationSource`. Use `IStringLocalizerFactory.Localize(permission.Description)` to obtain a translated string, and `Description.Value` to read the original text or format a dynamic permission template. Assign sources with `LocalizationSource.Create(value, typeof(DeclaringType))`. Modules compiled against a previous version must be recompiled.

### Deployment Step Labels

`DeploymentStep.Category` and `DeploymentStep.Title` are now `LocalizationSource` properties instead of `LocalizedString` properties. Custom steps must assign untranslated sources in their constructors, for example `Category = LocalizationSource.Create("Content", typeof(MyDeploymentStep))`, instead of resolving a localizer there. Use `IStringLocalizerFactory.Localize()` at display time. The properties remain excluded from persisted plans.

### Media Module

The former Media admin AJAX endpoints on `AdminController` (`MediaApplication`, `Upload`, `DeleteMedia`, `DeleteMediaList`, `MoveMedia`, `MoveMediaList`, `DeleteFolder`, …) have been removed and replaced by the `api/media` minimal-API endpoints described above. Custom code or themes calling those admin routes directly must migrate to the Media API (and account for its authentication scheme — cookie with antiforgery by default).

### `OrchardCore.Media.ImageSharpV3` Module Removed

The `OrchardCore.Media.ImageSharpV3` module and its **Media ImageSharp Image Processing** feature have been removed, together with the `OrchardCore.Media.ImageSharpV3` package and the `SixLabors.ImageSharp` dependency. Orchard Core no longer depends on ImageSharp, and images are always resized by the default NetVips engine.

Tenants that had the feature enabled keep working: the missing feature is ignored and the NetVips engine processes images. Remove any reference to the `OrchardCore.Media.ImageSharpV3` package from your projects and the feature from your recipes. To keep using ImageSharp, implement `IImageProcessingEngine` in your own project and replace the default registration as described in the [Media module documentation](../reference/modules/Media/README.md#image-processing-engines).

### Queries Module

`QueryApiController`'s `api/queries/{name}` endpoint previously handled both `GET` and `POST` through a single action sharing one `operationId` (`ApiExecuteQuery`), which OpenAPI does not allow to be reused across operations. It is now split into two actions — `ApiExecuteQueryGet` and `ApiExecuteQueryPost` — with no change to the endpoint's route, verbs, or parameters. If you generate an API client (e.g., with NSwag) against this endpoint, the generated method name(s) will change on your next regeneration.

### Liquid Module

The `{{ Site.SiteSalt }}` property of the `LiquidSiteSettingsAccessor` has been removed for security reasons.

The content of the `{{ Site.Properties }}` object is now redacted by default, because it can contain sensitive and security-critical data. To enable specific properties, you can configure the new `OrchardCore.Settings.SettingsLiquidOptions` object. For example using _appdata.json_:

```json
{
  "OrchardCore": {
    "Liquid": {
      "PermittedSiteProperties": [
        "ExternalRegistrationSettings",
        "ExternalLoginSettings",
        "CurrentThemeName",
        "CurrentAdminThemeName",
        "LayerSettings"
      ]
    }
  }
}
```

### Tenants Module

The `CreateTenantTask` workflow activity now runs the same `ITenantValidator` validation as the tenants admin UI and the tenants API before creating a tenant. A tenant name is used as a folder name (for example to resolve the tenant's media root), so an unvalidated name could redirect tenant-owned files outside of the tenant's directory.

Workflows that used to create a tenant with an invalid name, a duplicate request URL prefix and host, or a feature profile that does not exist, now take the `Failed` outcome instead. The validation errors are assigned to the workflow's `LastResult`.

`CreateTenantTask`'s constructor takes an additional `ITenantValidator` parameter. Code that constructs the activity directly instead of resolving it from the service provider must be updated.

## New features

### `OrchardCore.Antivirus` Module

The Antivirus module provides features that inspect uploaded files before Orchard Core stores or imports them permanently.

#### `OrchardCore.Antivirus.ClamAV` Feature

The ClamAV feature scans files with a `clamd` service before Orchard Core stores or imports them.

When the feature is enabled, uploads fail:

- Malware detections are rejected before storage.
- Scanner connectivity, timeout, or protocol failures also reject the upload.
- The ClamAV connection is reused per configuration to avoid creating a new TCP client for every scan.

This feature integrates with the shared file upload security pipeline through `IFileEventHandler`, so uploads can be rejected before Orchard Core stores them permanently.

### `OrchardCore.OpenApi` Module

This release introduces a new `OrchardCore.OpenApi` module that provides interactive API documentation and OpenAPI/Swagger schema generation for Orchard Core's API endpoints.

The module provides:

- three independently toggleable documentation UIs — Swagger UI, ReDoc, and Scalar — each as its own sub-feature;
- **zero-configuration silent authentication** for the "Try it out" flows: the Swagger and Scalar pages acquire an OAuth2 authorization-code + PKCE bearer token silently (`prompt=none` in a hidden iframe) using the signed-in admin's cookie session, auto-renew it, and attach it to every API request — no "Authorize" click and no authentication settings to fill in. Tokens are held in memory only, attached exclusively to same-origin `/api/` requests, and a token rejected by the server triggers one silent re-sign-in and retry;
- an **`OpenApiPkce` recipe** that provisions everything the silent flow needs: the OpenID Server/Validation/Management features, the authorization-code flow with PKCE required, local token validation, and a public secret-less `openapi` client registration;
- an `AllowAnonymousSchemaAccess` setting, **disabled by default**: the JSON schema endpoints require the `ViewOpenApiContent` permission unless it is enabled, so external tools like NSwag must either authenticate or run against a tenant that has opted into anonymous schema access;
- a `ViewOpenApiContent`/`ManageOpenApi` permission pair, so a role can be granted read-only access to the documentation UIs without also being able to change the module's settings;
- an `OpenApiGeneration` recipe that enables every feature exposing an API endpoint (Content, Queries, Tenants, Lucene, Elasticsearch) and turns on anonymous schema access, for generating client SDKs with tools like NSwag — plus a `tools/OpenApiClientGenerator` console tool that runs the whole NSwag regeneration pipeline headlessly and deterministically (operations are sorted by route + verb, so unchanged APIs regenerate byte-identical clients).

For configuration details and client generation steps, see the [OpenApi documentation](../reference/modules/OpenApi/README.md).

### `OrchardCore.RateLimits` Module

This release introduces a new `OrchardCore.RateLimits` module that centralizes request rate limiting for Orchard Core tenants.

When enabled, it provides:

- a configurable global fixed-window rate limit per remote IP address;
- route-specific rate limits that Orchard Core features can register by route name and HTTP method;
- centralized rate-limiter configuration so features such as Users and OpenID can protect sensitive endpoints without each feature registering its own middleware.

Static assets are excluded from the tenant rate limiter because the middleware is ordered after Orchard Core static-file handling. For configuration details, see the [Rate Limits documentation](../reference/modules/RateLimits/README.md).

### `OrchardCore.DataSources` Module

This release introduces a new `OrchardCore.DataSources` module that exposes the data of a site as typed, tabular data sets, read in batches with the access of a user:

- the content items of each content type, with their parts and fields, published or latest versions depending on the user's permissions; modules describe the values of their own parts and fields with `ContentDataSourceOptions`;
- the users of the site and their roles, to users who may view users, never exposing their passwords or other secrets;
- the results of the saved queries, with their parameters.

The module also provides the CSV, Excel, JSON and JSON Lines file formats, and a formula language with text, number, date, logical and aggregate functions. Modules add data sources with `services.AddDataSource<T>()` and file formats with `services.AddDataFileFormat<T>()`, and other features, such as reporting tools, can reuse them. See the [Data Sources documentation](../reference/modules/DataSources/README.md).

### `OrchardCore.DataPipelines` Module

This release introduces a new `OrchardCore.DataPipelines` module to design pipelines that read data, transform it, and deliver it, under **Tools** > **Data Pipelines**:

- a visual designer, with a step library, previews of the data of each step, drafts that save automatically, and published versions that can be restored;
- sources that read any data source or a data file of the media library; transforms that filter, calculate, select, sort, group, join, combine, deduplicate and limit rows; steps that create CSV, Excel and JSON files and zip them;
- destinations that save files to the media library, share them through secure, expiring download links, upload them to FTP and SFTP servers, send them to web APIs or by email, and create or update content items from rows;
- runs that execute in the background with the access of the user who published the pipeline, with a history of what each step did and delivered, and that workflows can start and react to;
- secrets, such as passwords and API keys, encrypted with the data protection keys of the tenant.

Modules add step types with `services.AddDataPipelineStep<TStepType, TDisplayDriver>()`. See the [Data Pipelines documentation](../reference/modules/DataPipelines/README.md).

### Page Size Selection

The **General** site settings now expose a **Page size selection** option. When an administrator enables it and provides a list of allowed page sizes (defaulting to `10, 25, 50, 100`), listing pages render an **Items per page** selector next to the pager. The list of options is only shown once the feature is enabled, and it is always stored as a sorted, de-duplicated list of positive numbers.

The selected value is passed as a `pageSize` query string parameter and is honored only when page size selection is enabled and the requested value is one of the configured options; any other value falls back to the default page size (the site default for admin listings, or the list's own page size for `ListPart` listings). The selection is carried across pages through the pager links, so no additional persistence is required.

The selector is rendered by the shared `Pager` and `PagerSlim` shapes, so it appears on both admin and front-end listings (including cursor-based `PagerSlim` lists such as blog posts) regardless of the active theme. The selector itself is the `Pager_PageSizeSelector` shape, which the `OrchardCore.Navigation` module implements by default with unstyled markup, so themes don't need to provide a template for it, but can provide one to style it, as `TheAdmin` and `TheTheme` do with Bootstrap. When the feature is disabled — the default — pagers render exactly as before.

The new `PagerOptions.AllowPageSizeSelection` and `PagerOptions.PageSizeOptions` values, together with the `PagerOptions.GetPageSize(int? selectedPageSize)` / `GetPageSize(int? selectedPageSize, int defaultPageSize)` helpers and the new `Pager(PagerParameters, PagerOptions)` constructor, let custom modules opt into the same validation. `PagerSlimParameters` now carries an optional `PageSize`. Existing calls that resolve the page size from the site defaults continue to work unchanged.

### Admin Breadcrumbs

Admin screens can now render a breadcrumb trail above their title. The `Breadcrumb` shape, provided by the always-enabled `OrchardCore.Navigation` module, renders the trail of pages leading to the page being displayed, e.g. _Manage Content › Edit Site Page_, as a small path above the page title; the current node's text is also rendered below the trail as the `<h1>`, so the screen keeps the title it had before, and its text is registered as a segment of the `<title>` of the page. How the trail and the title sit together is decided by a single template, `Breadcrumb.cshtml`, which a theme overrides to change the arrangement — for example to drop the heading and let the trail stand in for the title.

A view declares its current page with the `<breadcrumb>` tag helper's required `name` and `title` attributes. All inline `<breadcrumb-item>` children are ancestors, not the current page. Trail names and ancestor IDs are stable literal strings in Razor, while the helper assigns the current node the fixed `Id = "Title"`. Localized text comes from the view model or injected services:

```razor
<zone Name="Title">
    <breadcrumb name="ContentsEdit" title="@T["Edit {0}", contentItem.DisplayText]">
        <breadcrumb-item id="Contents" action="List" controller="Admin" area="OrchardCore.Contents">@T["Manage Content"]</breadcrumb-item>
    </breadcrumb>
</zone>
```

The required `title` is typed as `Microsoft.AspNetCore.Html.IHtmlContent`, including `LocalizedHtmlString`. `null` is invalid; empty content such as `Microsoft.AspNetCore.Html.HtmlString.Empty` suppresses heading and browser-title text but still produces the terminal current node in a visible trail. The stable `name` supports provider targeting, CSS classes, shape alternates, and Dashboard deduplication. Combined with the automatic current-node ID `Title`, it provides a screen-specific title alternate without a separate attribute.

Prefer the usual `@T[...]` result directly, including formatted arguments such as `title="@T["Edit {0}", record.Name]"`. Wrap plain strings with `new OrchardCore.DisplayManagement.Html.HtmlContentString(value ?? string.Empty)`. For `Microsoft.Extensions.Localization.LocalizedString` and `OrchardCore.Localization.Data.DataLocalizedString` from `IDataLocalizer`, wrap `.Value ?? string.Empty`. Never extract `T[...].Value` or substitute `Html.Raw`: the wrapper encodes untrusted strings. Ancestor child text remains `@T["..."]`.

When needed, the title follows one normalization path: render its `IHtmlContent` once via `WriteTo(writer, HtmlEncoder.Default)`, then HTML-decode once. The resulting plain string is safely encoded for the heading, current node, and browser title. Final output remains text-only, not arbitrary title markup. Literal entity text such as `&amp;` is preserved when its source string is safely wrapped.

For visible trails, after collecting ancestors, the helper awaits registered `OrchardCore.Navigation.IBreadcrumbProvider` implementations in DI registration order. The contract is `ValueTask BuildBreadcrumbAsync(BreadcrumbContext context)`. The context has read-only `Name`, `Title`, mutable ancestor-list `Items`, MVC `ViewContext`, and `ShowTrail` properties. `BreadcrumbContext.Title` is a normalized plain `string`, and its constructor is `BreadcrumbContext(string name, string title, List<BreadcrumbItem> items, ViewContext viewContext, bool showTrail)`. Helper-created provider contexts always have `ShowTrail == true`; hidden trails never create a context or invoke providers. Providers can add, insert, remove, replace, or edit ancestors, filtering the trail name or request explicitly. `services.AddBreadcrumbProvider<TProvider>()` registers providers as scoped services through `TryAddEnumerable`. Providers supply ancestors, not the current title; a provider-only declaration still requires an explicit title, for example `<breadcrumb name="Example" title="@T["Edit Example"]" />`.

Ancestor order follows the list: children are collected in declaration order, and providers can insert, remove, or reorder them. After providers finish, the parent helper preserves their final list order and unconditionally appends the explicit title node as final/current and never linked. This remains true if providers clear or reorder every ancestor; providers cannot remove or replace the current title. `BreadcrumbItem` has no `Position` property or `IPositioned` interface, and `<breadcrumb-item>` has no `position` attribute. Ancestors support MVC action routes, `route-*` parameters or a `route-values` dictionary (`IDictionary<string, string>`), direct URLs, permission names, authorization resources, and `link-enabled` (default `true`). A supplied `action` takes precedence over `url`. Unauthorized ancestors and those with `link-enabled="false"` remain visible as plain text. Child text is HTML-decoded, the normalized title and provider text are plain strings, and output is safely encoded.

`BreadcrumbItem.PermissionName` stores the child's `permission` name or one assigned by a provider; its existing `Permissions` list accepts `Permission` objects. Named permission lookup is deferred until visible ancestor link processing after providers, so removed and unlinkable ancestors never resolve the name. The explicit current node never needs link processing. Unknown permission names are ignored.

The helper defaults to `heading="h1"` and display type `DetailAdmin` on admin requests, and no heading and display type `Detail` on the front end. `page-title` defaults to `true` in both contexts. Visible trails use the existing `Breadcrumb` and `BreadcrumbItem` shapes and alternate factory. Current-title hooks are `BreadcrumbItem-Title.cshtml`, `BreadcrumbItem-[Name]-Title.cshtml`, `BreadcrumbItem-Title.[DisplayType].cshtml`, and `BreadcrumbItem-[Name]-Title.[DisplayType].cshtml`. Ancestor IDs and their alternates are unchanged. `IShapeFactory.BreadcrumbAsync` remains a low-level presentation API for prebuilt items; inline children are the authoring path for views.

Built-in admin views keep inline trails in place of their old title output. Nested editors use their models or existing services injected into Razor to resolve parent entities, such as a menu item's menu or a deployment step's plan. No required breadcrumb constants, `data` attribute, manager, builder, or named-provider base class is involved. Customize the owning view or its partials for screen-specific nodes, use lightweight providers for shared or cross-module postprocessing, and use shape alternates for presentation. `INavigationProvider` remains available for ordinary navigation menus.

Deployment steps gained a `LocalizedString DeploymentStep.Title`, set in the step's constructor next to `Category`, which is shown as the heading of the step's add and edit screens instead of a generic "Edit Step" — so the breadcrumb of a step reads, for example, _… › Export Content To Deployment Target_.

The `OrchardCore.AdminDashboard` feature registers `OrchardCore.AdminDashboard.Services.DashboardBreadcrumbProvider`. For visible trails, it checks `AdminAttribute.IsApplied(context.ViewContext.HttpContext)` and inserts a localized Dashboard ancestor at index `0` with ID `Dashboard`, unless `context.Name == "Dashboard"` or an ancestor already has that ID. It does not compare localized title text. Its URL is `"~/" + AdminOptions.AdminUrlPrefix`, and its `Permissions` list uses the static `OrchardCore.AdminDashboard.Permissions.AccessAdminDashboard` permission object. It can add Dashboard when no other ancestors exist, but never supplies the current title or changes front-end trails. Hidden admin trails skip this provider entirely.

The trail is on by default and can be turned off for the whole admin with the **Show breadcrumb** setting under _Configuration → Settings → Admin_ (`AdminSettings.ShowBreadcrumb`). A hidden helper never resolves, enumerates, constructs, or invokes `IBreadcrumbProvider` implementations, including Dashboard, and never calls `GetChildContentAsync`. It creates no `BreadcrumbContext` or breadcrumb items, including the current title node. There is no URL generation, permission lookup, link authorization, or shape creation.

Only the explicit title supplies hidden-state output. It is formatted once when a heading or browser title is needed; the heading is rendered directly with `oc-breadcrumb-title`, bypassing breadcrumb templates and alternates. A hidden helper with both `heading=""` and `page-title="false"` validates the non-null title but also skips `WriteTo`. Front-end trails are unaffected by the admin visibility setting and keep the full child/provider/rendering pipeline.

All **Show breadcrumb** decisions belong to the tag helper, not to views. Views declare the title and ancestors and resolve their needed data normally without reading `AdminSettings.ShowBreadcrumb` or guarding lookups or markup on that setting. Hidden trails always skip child-only work. Parent attribute expressions and Razor code or model lookups outside child content still run: `T[...]` results and wrappers are created before the helper, even when it skips `WriteTo`.

See the [Navigation documentation](../reference/modules/Navigation/README.md) for the full reference.

## Change Logs

### Configuration Section Names

The configuration sections are no longer prefixed with `OrchardCore_`. They are grouped by service instead, with a nested section for each provider of the service, so that all the settings of a service are located together. For instance, the `OrchardCore:OrchardCore_Email_Smtp` section is now `OrchardCore:Email:Smtp`, next to the `OrchardCore:Email:Azure` section, and the `OrchardCore:OrchardCore_Elasticsearch` section is now `OrchardCore:Search:Elasticsearch`, next to the `OrchardCore:Search:AzureAISearch` section:

```json
{
  "OrchardCore": {
    "Email": {
      "Smtp": {
        "DefaultSender": "site@example.com"
      }
    },
    "Media": {
      "Azure": {
        "ContainerName": "media",
        "ImageCache": {
          "ContainerName": "imagecache"
        }
      }
    },
    "Search": {
      "Elasticsearch": {
        "Url": "http://localhost"
      }
    }
  }
}
```

### Admin Quick Navigation

`OrchardCore.Admin` now includes a quick navigation palette, with its default view, navbar driver, JavaScript, and CSS provided by the module rather than an admin theme. ### Configurable Temporary File Storage

Orchard Core now writes temporary files (in-progress chunked and resumable TUS uploads, deployment and recipe import/export archives, and tenant recipe uploads) through a shared `ITempDirectoryProvider` abstraction (`OrchardCore.FileStorage`). The default `DefaultTempDirectoryProvider` implementation is filesystem-based and stores files under a tenant-scoped sub-directory of a configurable base path.

Previously these consumers wrote directly to the operating system temporary directory (`Path.GetTempPath()`), whose available space is often limited. Under heavy concurrent uploads of large files this could exhaust the temporary volume. The base location is now configurable through the `OrchardCore:TempDirectory` section:

```json
{
  "OrchardCore": {
    "TempDirectory": {
      // Point this at a larger or shared volume (e.g. a mounted Azure Files or AWS EFS/FSx share).
      // When omitted, the operating system temporary directory is used.
      "Path": "/mnt/shared/temp"
    }
  }
}
```

Resumable (TUS) partial uploads follow the same location (a `TusUploads` sub-directory), so `MediaOptions.TusTempPath` has been removed in favor of the single `OrchardCore:TempDirectory:Path` setting.

Because these consumers require random-access local files (for example `ZipFile.ExtractToDirectory` and `PhysicalFileProvider`), point `Path` at a mounted file share rather than object storage. Resumable (TUS) partial uploads can still target Azure Blob or AWS S3 object storage through the `ITusTempStore` implementations in the `OrchardCore.Media.Azure` and `OrchardCore.Media.AmazonS3` features.

Module authors that write temporary files should inject `ITempDirectoryProvider` (`GetRootDirectory()`, `GetTempFileName()`, `CreateTempSubdirectory()`) instead of calling `Path.GetTempPath()`, so their temporary files honor this configuration and stay scoped per tenant. On Unix-like operating systems, newly created tenant directories use owner-only permissions (`700`). The default `DefaultTempDirectoryProvider` is registered with `TryAddSingleton`, so it can be replaced with a custom filesystem-backed implementation. See the [Temporary File Storage documentation](../reference/core/temporary-file-storage.md) for configuration, mounting a file share, and consuming the interface.

The new `[RequiredStartup]` attribute causes a public component type to be composed for every tenant, even if the feature that defines it is disabled. The component and any services registered by its startup class are associated with `Application.DefaultFeatureId` rather than with the disabled feature. `[RequiredStartup]` can be combined with `[RequireFeatures(...)]`; in that case, the component is composed only when all required features are enabled.

### Azure Blob Storage Gen2 (ADLS Hierarchical Namespace) Support

`BlobFileStore` (used by Azure Media Storage and Azure Shells Configuration) now supports Azure Storage accounts with Hierarchical Namespace (HNS / ADLS Gen2) enabled, in addition to standard flat-namespace (Gen1) accounts.

- Before a namespace-sensitive operation, the store probes the account via `GetAccountInfo` to auto-detect whether HNS is enabled. Azure Media Storage also performs this probe during tenant activation.
- When HNS is detected, directory creation/deletion and file moves use native Azure Data Lake Storage APIs, giving atomic moves and real (non-virtual) directories instead of the marker-file emulation used on Gen1 accounts.
- A new `UseHierarchicalNamespace` setting on the Azure Media Storage configuration (`OrchardCore:Media:Azure`) lets you force Gen1 or Gen2 behavior when account-level detection is unavailable, such as when connecting with a container-scoped SAS token.
- The Data Lake SDK derives the account's DFS endpoint from the configured connection string, so no separate DFS endpoint setting is needed.

### API Error Responses

Error responses that opt out of the HTML error pages — the 401 and 403 responses produced by the shared `Api` authentication scheme, and the responses of endpoints marked with `[SkipStatusCodePages]` — now carry an RFC 9457 Problem Details body (`application/problem+json`), so headless clients get a parseable payload instead of an empty one. Responses that don't opt out are still handled by the status code pages middleware that the `OrchardCore.Diagnostics` feature registers.

Status codes and headers are left untouched: the `WWW-Authenticate` header of a challenge remains the responsibility of the authentication handler that issued it (e.g. the OpenID Token Validation feature, which emits the RFC 6750 header carrying the OAuth 2.0 error details). The body is written through `IProblemDetailsService`, so an application registering its own Problem Details customizations sees them applied to these responses too.

### `JavaScriptEngine` Constructor

`OrchardCore.Scripting.JavaScript.JavaScriptEngine` is public, and its constructor gained a third parameter, the registered `IGlobalMethodProvider` instances:

```csharp
public JavaScriptEngine(
    IMemoryCache memoryCache,
    IOptions<Jint.Options> jintOptions,
    IEnumerable<IGlobalMethodProvider> globalMethodProviders)
```

Resolving `IScriptingEngine` from the service provider is unaffected. Code that constructs the type directly — in practice, test code — has to pass the providers, and may pass an empty sequence to get the previous behavior.

### Globals Exposed by `IScriptingEngine.CreateScope()`

Every engine created by `JavaScriptEngine` now exposes the globals of the registered `IGlobalMethodProvider` instances, whether or not those methods appear in the `methods` argument of `CreateScope()`. Both in-tree callers always pass all of them, so this is not observable in Orchard Core itself, but a caller that deliberately passed a restricted set to hide a global no longer gets that effect. Methods passed in `methods` still take precedence over a registered global of the same name.

### JavaScript Prepared Script Cache

`JavaScriptEngine` caches the prepared (parsed) form of every script it evaluates in the shared `IMemoryCache`. Two problems were addressed:

- The cache entries were keyed on the raw script text, so a key registered by any other component could be read back as a prepared script and throw an `InvalidCastException`. The entries are now namespaced with a dedicated key type.
- `ScriptExternalLoginEventHandler` built its script by serializing the per-user context into the script source, which produced a unique script — and therefore a new cache entry holding a full syntax tree — for every external login. The context is now passed to the script through a scoped `externalLoginContext()` global method, so the cached script text only varies with the configured **Generate username** and **Sync properties** scripts.

### JavaScript Rule Condition Validation

Saving a JavaScript rule condition that contains a syntax error no longer fails with an unhandled exception. `Engine.PrepareScript()` wraps parser failures in `Jint.ScriptPreparationException`, which is now caught by the condition editor and reported as the intended validation message.

### JavaScript Engine Update

The bundled JavaScript engine, Jint, was updated. Besides enabling the lazy globals described below, it changes two things that matter to sites configuring `IOptions<Jint.Options>`:

- **The execution-constraint helpers are now safe on the shared options instance.** `MaxStatements()`, `TimeoutInterval()`, `LimitMemory()` and `CancellationToken()` register a factory rather than a constraint object, so each engine gets its own statement counter and its own deadline. One `Jint.Options` is shared by every engine of a tenant, so before this a configured constraint would have shared its per-execution state — and its resets — between concurrently running requests. Registering a constraint *instance* through `options.Constraint(constraint)` still shares it; use the `options.Constraint(() => new MyConstraint())` overload.
- **Resolved CLR members are now cached across engines** rather than per engine. Since a new engine is built for nearly every evaluation, the reflection to resolve and compile access to a member of `HttpContext`, `ContentItem` or a workflow context used to be repeated for each one.

Three further changes arrived with the update to Jint 4.16.0 and are visible to script authors:

- **Machine-readable output no longer depends on the server's culture.** `JSON.stringify()` and `Date.prototype.toISOString()` now always format invariantly. On a site whose threads ran under a culture that writes negative numbers with a Unicode minus — Swedish, Finnish, Norwegian, Lithuanian and Estonian among them — a script serializing a negative number produced output that no JSON parser accepts. A workflow or recipe that worked in one deployment and failed in another for no visible reason is the shape of this bug.
- **`JSON.parse()` rejects trailing commas.** `JSON.parse('[1,2,]')` now throws, as the JSON grammar requires. A script relying on the previous leniency has to drop the trailing comma.
- **Sorting with an inconsistent comparator no longer escapes the script.** A comparison function that answers differently for the same pair used to fail with a CLR exception that no `try`/`catch` in the script could handle. It now finishes with an unspecified order, so the script stays in control.

The update to Jint 4.17.0 changes a few more things a script author can run into:

- **An asynchronous script no longer repeats its earlier statements.** Reading an element or a computed member straight off an awaited value — `(await executeQueryAsync('recent', {}))[0]`, or `(await deserializeRequestDataAsync())[name]` — made the async function run every statement before that point a second time. Awaited calls were not repeated, but anything the function did without awaiting was: a `createContentItem(...)` or `responseWrite(...)` placed before such a read, or a `createContentItemAsync(...)` that was not awaited, ran twice, producing a duplicate content item or duplicate output.
- **More scripts can no longer end the process.** A script that builds a long prototype chain — `Object.create()` in a loop — and then reads, writes or tests a property on it (`x.y`, `x.y = 1`, `'y' in x`, or a name inside `with (x)`), and a script that builds a long `.bind()` chain and then uses the result with `new`, `Reflect.construct()` or `class ... extends`, both overflowed the native stack the same way unbounded recursion did, and `Constraints.StackOverflowGuard` did not catch them. The first now resolves normally at any depth. A long chain of proxies, which cannot be walked that way, and `new` or `Reflect.construct()` on the `.bind()` chain now either complete normally or, when the stack runs low, raise an ordinary `RangeError`; `class ... extends` raises the `TypeError` for a superclass without a `prototype`. The same was true of an `eval` that keeps evaluating itself (`var s = 'eval(s)'; eval(s)`, also with `eval` as an object's `Symbol.hasInstance` method), which now raises a `RangeError`, and of an error passed back out of a `ShadowRealm` through its wrapped functions; a call through a long chain of such functions now either completes normally or raises a `TypeError`. Every one of these errors can be caught by the script, and the protection relies on the guard that `AddJavaScriptEngine()` turns on. How deep a structure has to be before the error is raised depends on the size of the stack, so the same script may complete on one server and raise the error on another; on neither does it end the process.
- **Building a string with `s = s + x` is no longer slow.** Each `+` used to copy the whole string built so far, so a loop appending that way took time that grew with the square of the string's length; it now grows linearly, as `s += x` already did. A memory limit set with `LimitMemory()` still counts the string.
- **`concat()` spreads arrays and lists returned by .NET methods.** `['a'].concat(list)`, where `list` came from a .NET method, added the list as a single element instead of its items.

See the [Scripting documentation](../reference/modules/Scripting/README.md#configuring-the-javascript-engine) for the current behavior.

### The Scripting Cancellation Token Now Stops the Script

`IScriptingManager.EvaluateAsync()` and `IScriptingEngine.EvaluateAsync()` have always accepted a `CancellationToken`, and it did not bound the script. Jint's `EvaluateAsync` observes a token only while awaiting promise settlement — the script is interpreted to completion first — so the token bounded an evaluation that awaited something, and nothing at all for one that did not. Passing an already-cancelled token still ran a script to the end.

`AddJavaScriptEngine()` now registers a `Jint.Constraints.OperationDeadlineConstraint` factory, which Jint 4.16.0 added for exactly this shape, and `JavaScriptEngine.EvaluateAsync()` arms that engine's instance with the token of the call it is serving. Cancelling now stops the interpreter, and surfaces as `OperationCanceledException` carrying the token rather than as a scripting error.

No time budget is introduced: the constraint is armed with `Timeout.InfiniteTimeSpan`, its cancellation-only shape, so how long a script may run remains a policy a site sets through `IOptions<Jint.Options>`. A token cancelled before the call is observed before the script starts; one cancelled while the script runs is observed on the engine's amortized constraint cadence, which is what keeps the interpreter's tight-loop fast path armed.

A module that passed a token was silently getting no cancellation and now gets it. The scripts Orchard Core runs itself now pass the token that naturally bounds them:

- **Workflows**: every JavaScript expression of a workflow is bounded by `WorkflowExecutionContext.CancellationToken`, so `WorkflowExecutionContext.Cancel()` stops a script that is running instead of waiting for it to finish. The stopped script faults the workflow at the activity that was running it, as described under [Workflow Scripts Stopped by an Execution Limit Fault the Workflow](#workflow-scripts-stopped-by-an-execution-limit-fault-the-workflow).
- **Rules** (and therefore layers): a JavaScript condition is bounded by `HttpContext.RequestAborted`, so a script still running when the client disconnects is stopped. The `OperationCanceledException` propagates like any other cancellation of an aborted request.
- **Recipes**: the `[js: ...]` expressions of a recipe step are bounded by the token passed to `IRecipeExecutor.ExecuteAsync()`. Cancelling it while a step's script runs now fails that step with a `RecipeExecutionException` wrapping the `OperationCanceledException`; previously the script ran to completion and the recipe stopped before its next step. Only setup passes a token that can be cancelled — the application's stopping token.

The `variables()` of a recipe and the external login scripts of the Users module have no token available and are still unbounded by cancellation.

### Unbounded JavaScript Recursion No Longer Kills the Process

`AddJavaScriptEngine()` now turns on Jint's `Constraints.StackOverflowGuard`.

An unbounded recursion in a script — `function f() { return 1 + f(); }`, and equally a getter, a constructor or a `valueOf` that re-enters itself — overflowed the native stack, and a native stack overflow is not an exception: it cannot be caught, nothing is logged, and the runtime ends the whole process rather than the one request. A site that had followed this module's advice and configured execution constraints was not protected either, because a budget is only reached by a script that survives long enough to spend it and the overflow arrives in milliseconds. With `MaxStatements(10_000)` and `TimeoutInterval(TimeSpan.FromSeconds(5))` both set, such a script still ended the process.

It now raises an ordinary `RangeError` that the script itself can catch, only the request that ran it fails, and the engine is still usable afterwards.

Older Jint versions let other script shapes overflow the native stack where the guard did not see them, such as a property access on a very long prototype chain, `new` on a function made by a very long `.bind()` chain, or an `eval` that keeps evaluating itself. Since Jint 4.17.0 these are covered too, as described under [JavaScript Engine Update](#javascript-engine-update).

The guard measures the remaining stack at every entry into a script function, which Jint's own benchmarks put at 1.7–2.3% on deeply recursive code and unmeasurable on ordinary calls. Because it is set on the registration rather than on the engine, an application that has weighed that against its own scripts can turn it off with its own `Configure<Jint.Options>` call:

```csharp
services.Configure<Jint.Options>(options =>
{
    options.Constraints.StackOverflowGuard = false;
});
```

### Request Values in Workflow Scripts Are Strings

`deserializeRequestData()` — and `queryStringAsJson()` and `requestFormAsJson()`, which call it — returned the query string and form fields of a request as objects rather than strings. A script comparing one with `===` always got `false`, `typeof` answered `"object"`, string methods such as `toUpperCase()` did not exist, and `JSON.stringify()` wrote a single value as `{"Length":4}`. The values are now converted the way `queryString()` and `requestForm()` already converted them: a string when the field has one value, a list of strings when it has several, and `null` when it has none.

A value read directly from the ASP.NET Core request, such as `httpContext().Request.Query['name']`, is still an object rather than a string, but comparing it with `==` or concatenating it with a string no longer throws `Method 'toString' called on incompatible receiver`. Use `queryString('name')` or `requestForm('name')` when the script needs a string.

### Lazily Registered JavaScript Globals

The globals contributed by `IGlobalMethodProvider` implementations are no longer created up front for every engine. `JavaScriptEngine` declares them on the shared Jint options with `Options.AddLazyGlobal()`, so each engine gets a lazy property per global and the delegate behind it is only built when a script reads the name. Because `DefaultScriptingManager` creates an engine per evaluation, a directive such as `[js:uuid()]` used to install every registered global — around forty on a typical site — in order to call one of them.

Points worth knowing:

- The properties themselves are installed as before, so `in`, `hasOwnProperty()` and `Object.getOwnPropertyNames()` still see every global. They remain non-enumerable, so `Object.keys(globalThis)` does not list them, exactly as with `Engine.SetValue()`.
- The value is cached by the engine after the first read, so the identity of a global is stable for the whole evaluation.
- Deleting a global before ever reading it means its delegate is never built. Assigning to it or redefining it does build it once and then discards the result. The end state is correct in every case; only the laziness is lost.
- Every engine created by `JavaScriptEngine` exposes the globals of the registered method providers, whether or not they appear in the `methods` argument of `IScriptingEngine.CreateScope()`. Methods that are not registered by a provider — the ones a caller adds for a single evaluation, such as a recipe's `variables()` or a workflow's `workflow()` — are still installed eagerly, and take precedence over a registered global of the same name.

`JavaScriptEngine` now takes the registered `IGlobalMethodProvider` instances as a constructor parameter; code that resolves `IScriptingEngine` from the service provider is unaffected.

The services a global is created from travel on the engine itself, in the `Engine.Advanced.HostDefined` slot Jint reserves for the hosting application and never reads. Modules do not have to do anything for this, but two things follow from it: do not write to that slot on an engine obtained through `JavaScriptScope.Engine`, and a scope built around an engine of your own claims the slot only if nothing else has already, so an engine you are using it on yourself keeps what you put there.

### Workflow Scripts Stopped by an Execution Limit Fault the Workflow

The JavaScript evaluator of the Workflows module caught every exception a script raised, logged it and returned the default value of the expression — `null`, `false` or `0`. That is still what happens when a script throws an error, does not parse, or returns a value that cannot be converted to the type of the expression. It no longer happens when the script was stopped before it produced any value: by one of the limits a site configures on `Jint.Options` (`MaxStatements()`, `TimeoutInterval()`, `LimitMemory()`, `LimitRecursion()`, `CancellationToken()`), or by the cancellation token of the evaluation. Previously such a script turned into a `false` condition or a `null` value and the workflow carried on down an outcome nobody decided on — an `If/Else` whose condition ran out of time took its `False` branch.

These exceptions — `OperationCanceledException`, `TimeoutException`, and Jint's `StatementsCountOverflowException`, `MemoryLimitExceededException`, `RecursionDepthOverflowException` and `ExecutionCanceledException` — now leave the evaluator. When the script belongs to an activity, the workflow is faulted at that activity, which logs the error and triggers the **Workflow Fault** event, like any other activity failure. A script evaluated outside an activity's execution, such as the error filter of a **Workflow Fault** event, now lets the exception reach whoever triggered the workflow. An `OperationCanceledException` or `TimeoutException` thrown by a .NET method the script calls is treated the same way.

Sites that configure no execution limit are only affected through cancellation. A rejected promise, including one rejected because `Jint.Options.Constraints.PromiseTimeout` elapsed, is still treated as a script error: Jint reports both as the same `PromiseRejectedException`.

### Direct Acornima Dependency

`OrchardCore.ContentFields`, `OrchardCore.Html` and `OrchardCore.Markdown` use `Acornima.Parser` to validate editor settings and reached it transitively through Jint. They now reference Acornima directly and no longer reference Jint.

### Multiple Content Types and Stereotypes in the Admin Contents List

The `Contents` admin list action now supports filtering by multiple content type IDs or stereotypes while preserving the existing parameter names.

- Pass `contentTypeId` as repeated query-string values or as a comma-separated list to scope the list to several content types (e.g. `?contentTypeId=Article&contentTypeId=BlogPost` or `?contentTypeId=Article,BlogPost`).
- Pass `stereotype` as repeated query-string values or as a comma-separated list to scope the list to content types that match any value (e.g. `?stereotype=Widget&stereotype=Page` or `?stereotype=Widget,Page`).
- Existing single-value route and query-string parameters continue to work as before.

### Available Filters Dialog Redesign

The **Available Filters** dialog (the **Filter syntax** entry in the **Filters** dropdown of the content items, users, and audit trail admin lists) was redesigned. The filter cards, previously stacked full-width one per row, are now laid out in a compact responsive grid, and the dialog was widened to `modal-xl`.

This changes the markup contract of the per-filter *Thumbnail* templates. Custom filter cards still render — each is wrapped in a grid cell automatically — but a card that keeps the old markup will look out of place next to the built-in ones. If your module registers its own filter card (a `*AdminFilters-*.Thumbnail.cshtml` view contributed through a `DisplayDriver<ContentOptionsViewModel>`, `DisplayDriver<UserIndexOptions>`, or `DisplayDriver<AuditTrailIndexOptions>`), update its template to the new layout:

**Before:**

```html
<div class="ocat-wrapper">
    <h4 class="card-title ocat-label">@T["Display Text"]</h4>
    <div class="ocat-end">
        <pre>@(term?.ToString() ?? "text:...")</pre>
    </div>
</div>
<p>@T["Filters on the Display Text of a content item."]</p>
<div class="d-block text-end">
    <span><i class="fa-solid fa-sm fa-check text-primary" aria-hidden="true"></i></span>
    <span><i class="fa-solid fa-sm fa-bars text-primary" aria-hidden="true"></i></span>
</div>
```

**After:**

```html
<div class="d-flex justify-content-between align-items-center gap-2">
    <h6 class="card-title fw-semibold mb-0">@T["Display Text"]</h6>
    <span class="text-primary text-nowrap">
        <i class="fa-solid fa-sm fa-check" title="@T["Default term - may be entered with or without the term name"]" aria-hidden="true"></i>
```

The template now provides only the card's inner content — the surrounding `.card` and grid cell are supplied for you. Put the title and its capability icons on the first line, the filter token on the next line, and the description last. Keep using the shared capability icons — `fa-check` (Default), `fa-minus` (Single), and `fa-bars` (Multiple) — so the legend at the bottom of the dialog stays accurate.

If your module also overrides the grid container or card wrapper shapes (`ContentOptionsViewModel.Thumbnail.cshtml` / `UserIndexOptions.Thumbnail.cshtml` / `AuditTrailIndexOptions.Thumbnail.cshtml`, or the `*AdminFilters-Card.Thumbnail.cshtml` wrappers), re-check those overrides against the new templates, which now emit `row row-cols-*` and `col > card h-100` markup.

See the [content filters documentation](../reference/modules/Contents/README.md#documenting-filters-in-the-admin-ui) and the [users filters documentation](../reference/modules/Users/README.md#documenting-filters-in-the-admin-ui) for the full extension guide.

### Theme Feature Discovery

Fixed theme extensions disappearing from the Themes admin page when the assembly manifest included additional `[Feature]` attributes alongside `[Theme]`. Extra
features now appear correctly with their category and Enable button in the Features admin. See [#19160](https://github.com/OrchardCMS/OrchardCore/issues/19160).

`IFeaturesProvider` implementations are now resolved as a collection via `IServiceProvider.GetServices<IFeaturesProvider>()` instead of a single required
service, allowing subsystems such as `OrchardCore.DisplayManagement` to contribute their own feature providers without introducing theme-awareness into
core (`OrchardCore.Extensions.ExtensionManager`).

### File Upload Security

Orchard Core now provides a file upload event pipeline for securing user-uploaded files before they are stored:

- `IFileEventHandler`
- `FileCreatingContext`
- `FileCreatingResult`
- `FileCreationService`

Use `FileCreationService.CreateAsync()` anywhere your code accepts a user-uploaded file and stores it directly. If the returned `FileCreatingResult.Succeeded` value is `false`, you must abort the upload and avoid persisting the file. Only call `FileCreationService.CreatedAsync()` after the file was stored successfully.

### Duplicate Endpoint Name Link Generation

Generating a link to an attribute-routed API endpoint by its name (`LinkGenerator.GetPathByName()` / `GetUriByName()`), for example the `[EndpointName]`-decorated actions in `OrchardCore.Queries`, `OrchardCore.Elasticsearch` and `OrchardCore.Tenants`, could throw an `InvalidOperationException` reporting duplicate endpoint names.

When a tenant maps a dynamic controller route (as `OrchardCore.Autoroute`, `OrchardCore.HomeRoute` and `OrchardCore.Sitemaps` do), the shared controller endpoint data source also emits a second, non-routable placeholder endpoint for every action, copying the action metadata — including its `[EndpointName]`. For attribute-routed actions this collided with the routable endpoint's name, and the framework's endpoint-name address scheme throws as soon as two link-generating endpoints share a name.

`OrchardCore.Mvc` now removes endpoint-name metadata from these non-routable placeholders while preserving it on the real attribute-routed endpoints. Named link generation therefore resolves a single route endpoint, while genuine duplicate endpoint names continue to be rejected by the framework.

### Background Tasks Bulk Actions

The **Background Tasks** admin list (`/Admin/BackgroundTasks`) now supports bulk actions, similar to the **Features** admin list. Each task has a checkbox, and once more than one task is selected an **Actions** menu appears with **Enable** and **Disable** options that apply to every selected task at once. The list uses the shared `list-management` script, so the per-page **Select All** checkbox and selection count behave consistently with the other admin lists.

### Features Bulk Actions

The **Toggle** bulk action was removed from the **Features** admin list, leaving **Enable** and **Disable**, for consistency with the other admin lists that offer bulk actions. The `Toggle` value was also removed from the `FeaturesBulkAction` enum and its handling in `FeatureService.EnableOrDisableFeaturesAsync`.

### OpenID Server Logout Without Confirmation

Disabling `RequireEndSessionConfirmation` in the OpenID server settings now signs users out without a confirmation prompt, as intended. Previously the prompt was always shown, because OpenIddict didn't return the principal of the `id_token_hint` when end session request caching was enabled. This was fixed in OpenIddict 7.7.1, which Orchard Core now references. The local authentication cookie is now also removed when the prompt is skipped.

The `id_token_hint` must be a valid identity token issued for the currently authenticated user. Otherwise, the confirmation prompt is still shown.

`RequireEndSessionConfirmation` can now also be set by the `OpenIdServerSettings` recipe step and is included in deployment plans. When omitted from a recipe, it defaults to `true`.

### Deferred Localization Sources

`OrchardCore.Abstractions` adds an immutable `LocalizationSource` containing an untranslated `Value` and an optional source `Type`. Declare sources with `LocalizationSource.Create(value, type)` or `LocalizationSource.Create<T>(value)` so source-extraction tools can discover explicit calls without inferring target-typed constructor syntax. External extractor support is separate from Orchard Core's runtime localization. The new `IStringLocalizerFactory.Localize()` and `IHtmlLocalizerFactory.Localize()` extensions resolve the source type's localizer at display time, with optional format arguments. The rendering call site chooses text or HTML localization; the source does not translate, format, or encode its value. See [Deferring localization](../reference/modules/Localize/README.md#deferring-localization-with-localizationsource).

`OrchardCore.Localization.Abstractions` adds matching `IStringLocalizerFactory.Plural()` and `IHtmlLocalizerFactory.Plural()` extensions, taking a count, a singular `LocalizationSource`, the plural text, and optional format arguments inserted after the automatically prepended count. For a context-bearing source they delegate to the existing `Plural()` extension on the resolved localizer, so culture-specific PO plural rules (including a zero form or more than two forms) still apply; for a context-free source they fall back to the English singular/plural rule. See [Pluralizing a deferred LocalizationSource](../reference/modules/Localize/README.md#pluralizing-a-deferred-localizationsource).

### Localized Permission Descriptions

The built-in permissions now create their descriptions with `LocalizationSource.Create(description, typeof(DeclaringType))`. The roles editor, and the permission pickers of admin menu nodes and menu items, now show the PO file translation of these descriptions. Because these descriptions are translated with PO files, they are no longer listed in Data Localization, and translations of them that were entered in Data Localization are no longer used. Context-free descriptions, including the permissions built from templates such as "Edit Article", and permission categories continue to be translated with Data Localization. See [Declaring permissions](../reference/modules/Roles/README.md#declaring-permissions).

### Deployment Step Categories and Titles

The built-in deployment steps now assign static readonly `LocalizationSource` instances to their `Category` and `Title` properties in their parameterless constructors, avoiding per-step allocations for these labels. The constructors that took an `IStringLocalizer<TStep>` only to set them were removed. The deployment plan page and the step screens translate these sources with `IStringLocalizerFactory.Localize()`, retaining the same contexts and keys as the previous typed localizers so existing PO translations continue to work. See [Extending deployment](../reference/modules/Deployment/README.md#extending-deployment).
